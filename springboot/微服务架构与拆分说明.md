# 开罗论坛（Cairo Forum）微服务架构与拆分说明

> 本文回答两个问题：
> 1. 本项目是如何实现并使用微服务的；
> 2. 若要把微服务拆分/迁移到其它主机，应该分离哪些代码、保留哪些代码。

---

## 一、项目概览：微服务是如何划分的

本项目是一个基于 **Apache Dubbo + ZooKeeper** 的 RPC 微服务架构，用 **Maven 多模块**组织代码。
整体可拆分为 **4 个可独立部署的进程 + 若干共享依赖模块**。

### 1.1 模块目录结构

```
ns-bbs (父 POM：com.liang:ns-bbs，仅做版本/依赖/插件统一管理)
│
├── bbs-rest                        # ① REST 网关层（对外入口，Dubbo 纯消费者）
│
├── bbs-common                      # ② 公共模块（枚举/常量/工具类）
│
├── bbs-user                        # ③ 用户域微服务（父 POM）
│   ├── bbs-user-facade             #     接口契约 + DTO（Dubbo 接口层）
│   ├── bbs-user-persistence        #     数据访问层（entity + mapper）
│   └── bbs-user-service            #     服务实现（Dubbo 提供者，可执行应用）
│
├── bbs-article                     # ④ 文章域微服务（父 POM，同 user 三层结构）
│   ├── bbs-article-facade
│   ├── bbs-article-persistence
│   └── bbs-article-service
│
└── bbs-auth                        # ⑤ 鉴权微服务（自托管，替代作者的 ns-manage 服务）
```

### 1.2 四个可部署进程的端口与职责

| 服务 | 应用名 `spring.application.name` | HTTP 端口 | Dubbo 端口 | 依赖数据库 | 角色 |
|------|--------------------------------|----------|-----------|-----------|------|
| `bbs-rest` | `ns-bbs-rest` | 7010 | 22001 | 无（纯消费者） | REST 网关 / Dubbo 消费者 |
| `bbs-article-service` | `ns-bbs-article` | 7011 | 22002 | MySQL `open_bbs` + MongoDB `open_bbs` | 文章域：提供者 + 消费者 |
| `bbs-user-service` | `ns-bbs-user` | 7013 | 22003 | MySQL `open_bbs` | 用户域：提供者 + 消费者 |
| `bbs-auth` | `ns-bbs-auth` | 7014 | 22004 | MySQL `ns_auth` | 鉴权：提供者 |

> 端口值来源于各服务的 `application.yml`（`server.port` 与 `dubbo.protocol.port`）。

## 二、微服务是如何实现的

### 2.1 RPC 框架：Dubbo + ZooKeeper

- **注册中心**：ZooKeeper（`dubbo.registry.address: zookeeper://127.0.0.1:2181`），四个模块必须指向**同一个地址**，这是服务互相发现的前提。
- **接口级注册**：所有服务统一配置 `register-mode: interface` 与 `migration.step: FORCE_INTERFACE`，强制使用接口级服务注册（而非 Dubbo 3 默认的应用级服务发现）。
- **通信协议**：`dubbo` 协议，每个进程占用独立的 Dubbo 端口（22001~22004）。

### 2.2 三层模块拆分（典型 Dubbo 项目分层）

每个业务域（user / article）都按**三层**拆分，职责边界非常清晰：

| 层 | 模块 | 内容 | 谁依赖它 |
|----|------|------|---------|
| **接口层（契约）** | `*-facade` | `facade.server.*` 接口 + `facade.dto.*` DTO | 消费者、提供者**都**依赖 |
| **数据层** | `*-persistence` | MyBatis 的 `entity`（Po/PoExample）+ `mapper`（Mapper 接口 + `mybatis/mappers/*.xml`） | **只有** `*-service` 依赖 |
| **实现层（可执行）** | `*-service` | `impl` 实现类 + `mapstruct` 转换 + `config` + 启动类 + `application.yml` | 可独立打包运行 |

关键点：**facade 是契约、persistence 是私有实现、service 是运行单元**。

### 2.3 关键注解与调用方式

- **服务提供者（provider）**：
  - 启动类用 `@EnableDubbo` 开启（`bbs-user-service` 的 `UserApplication.java:12`）。
  - `@DubboComponentScan(basePackages = "...service.impl")` 扫描实现类（`DubboConfig.java:13`）。
  - 实现类标注 `@Service`（`org.apache.dubbo.config.annotation.Service`），如 `FollowServiceImpl.java:40`。

- **服务消费者（consumer）**：
  - 注入远程接口用 `@DubboReference`，如 `ArticleController.java:43` 注入 `ArticleService`。

### 2.4 服务间调用关系（依赖拓扑）

```
                 ┌────────────────────────────┐
   外部请求 ───▶ │  bbs-rest (REST 网关)        │
                 │  @DubboReference 调用各服务   │
                 └───┬──────────┬──────────┬───┘
                     │          │          │
             ┌───────▼──┐  ┌────▼──────┐  ┌▼─────────┐
             │ article  │◀▶│  user     │  │  auth    │
             │ -service │  │ -service  │  │(鉴权/SSO)│
             └──────────┘  └───────────┘  └──────────┘
                 ▲                ▲
                 └──── 双向 RPC ────┘
```

- `bbs-rest` 是唯一对外入口，通过 `@DubboReference` 调用 `bbs-user-facade`、`bbs-article-facade`（以及 auth 的 `UserService`）的接口。
- `article-service` 与 `user-service` 存在**双向 RPC**：
  - article 调 user 的 `LikeService` / `FollowService` 等；
  - user 调 article 的 `ArticleService`（`FollowServiceImpl.java:48-49`）。
- `user-service` 还调用 auth 的 `com.liang.manage.auth.facade.server.UserService`（该接口来自第三方 `nansheng-common` jar，见 `FollowServiceImpl.java:45-46`）。

### 2.5 基础设施清单

| 组件 | 地址（当前） | 用途 |
|------|-------------|------|
| ZooKeeper | `127.0.0.1:2181` | Dubbo 注册中心 |
| MySQL | `127.0.0.1:3306` | `open_bbs`（业务库，user/article 共用）、`ns_auth`（鉴权库） |
| Redis | `127.0.0.1:6379` | SSO token、验证码、点赞/关注等缓存 |
| MongoDB | `127.0.0.1:27017` | 文章内容（仅 article-service 使用） |
| 七牛云 / 阿里云短信 / 邮件 | 外部 | 文件存储、短信、邮件（可选） |

## 三、拆分到其它主机：分离哪些、保留哪些

### 3.1 核心结论（先记住这两点）

1. **本项目已经具备拆分基础**：每个 `*-service` 本身就是可独立打包、独立运行的 Spring Boot 应用（有自己的 `main` 启动类、`application.yml`、`spring-boot-maven-plugin` 打包、`assembly.xml` 打成 zip）。因此"迁移到其它主机"主要不是改代码，而是**改配置 + 解决依赖共享**。
2. **真正要动的只有一件事——facade 契约的共享方式**。Dubbo 靠"接口全限定名 + 版本"来匹配消费者与提供者，所以**消费者和提供者必须拿到完全相同的 facade 接口类**。单机单仓库时靠 Maven 本地 reactor 直接依赖；跨主机后必须把 facade 发布到 Maven 私服共享。

### 3.2 代码归属：分离哪些、保留哪些

按"部署目标主机"重新划分代码，建议如下：

**A. 每个服务"带走"的代码（跟随服务独立部署）**

| 服务 | 带走的模块（代码） | 说明 |
|------|------------------|------|
| 用户服务 | `bbs-user-service` + `bbs-user-persistence` | service 是运行单元；persistence 是它的私有依赖，随服务走，**不单独部署到别处** |
| 文章服务 | `bbs-article-service` + `bbs-article-persistence` | 同上 |
| 鉴权服务 | `bbs-auth` | 自托管鉴权，独立部署 |

> `persistence` 层代码属于对应服务，但因为数据库访问不跨主机，它只会被自己的 `service` 引用，所以它**不需要**单独部署到消费者（bbs-rest）所在主机，也不需要单独运行。

**B. 必须"保留并共享"的代码（所有主机都要能拿到同一份）**

| 模块 | 为什么必须共享 | 共享方式 |
|------|--------------|---------|
| `bbs-user-facade` | 消费者（bbs-rest、article-service）和提供者（user-service）都必须引用同一份接口 | 发布到 Maven 私服，各方按**相同版本号**拉取 |
| `bbs-article-facade` | 同上（bbs-rest、user-service ↔ article-service） | 同上 |
| `bbs-common` | 枚举/常量/工具，被所有 facade 依赖 | 发布到私服 |
| `nansheng-common`（第三方） | 提供 `com.liang.manage.auth.facade.server.*` 接口契约 + 公共工具 | 已是从远程仓库拉取的第三方 jar，保持可用即可 |

> ⚠️ **facade 是分离的核心与最大的坑**：如果消费者和提供者各自从私服拉到**不同版本**的 facade，Dubbo 会因为接口版本不一致而调不通（No provider / 找不到服务）。所以 facade 必须有明确的版本管理，且改接口后要同时升级并通知所有消费方。

**C. 需要"保留在原处"的代码**

- `bbs-rest`（REST 网关）：通常保留，作为统一对外入口。也可以独立部署，但它本身不含业务数据。
- 父 POM `ns-bbs`：作为构建根，保留；若彻底拆成多仓库，则需为每个服务单独建立父 POM 并继承版本管理。

### 3.3 配置需要改的地方（迁移到其它主机必改）

每个服务的 `application.yml` 里，把中间件地址从 `127.0.0.1` 改成实际所在主机：

| 配置项 | 当前值 | 改法 |
|--------|--------|------|
| `dubbo.registry.address` | `zookeeper://127.0.0.1:2181` | 改成所有主机都能访问的 ZooKeeper 地址（服务发现枢纽，**四个服务必须一致**） |
| `spring.datasource.url` | `jdbc:mysql://127.0.0.1:3306/...` | 改成 MySQL 所在主机 |
| `spring.data.redis.host` | `127.0.0.1` | 改成 Redis 所在主机 |
| `spring.data.mongodb.uri`（仅 article） | `mongodb://127.0.0.1:27017/...` | 改成 MongoDB 所在主机 |
| `auth.file-url-prefix`（仅 auth） | `http://127.0.0.1:7014/static/` | 改成 auth 服务的对外地址 |
| `dubbo.protocol.port` | 22001~22004 | 跨主机可**保持不变**（IP 不同即可区分），注意放行防火墙端口 |

### 3.4 需要注意的决策点

1. **共享库 vs 拆库**：当前 `open_bbs` 被 `article-service` 和 `user-service` **共用一个 MySQL 库**。拆到两台主机后，要么（a）保留一个共享 MySQL 实例、两个服务远程连接；要么（b）按域拆库（用户表归 user、文章表归 article），但需同步改动 mapper 与 SQL，工作量较大。
2. **facade 版本治理**：引入私服后，`*-facade`、`bbs-common` 需要 `mvn deploy` 发布并锁版本，避免接口漂移。
3. **双向 RPC 的耦合**：`article` ↔ `user` 双向调用，意味着两套服务必须同时在线并连到同一个 ZooKeeper，否则互相调用会失败（`consumer.check: false` 下表现为运行时异常）。拆分时建议规划好启动顺序与容错。

### 3.5 最小拆分步骤（以拆出 user 服务为例）

1. 把 `bbs-user-facade`、`bbs-common`（以及依赖的 `nansheng-common`）发布到 Maven 私服，锁定版本。
2. 在目标主机上，`mvn package` 打包 `bbs-user-service`（会连同 `bbs-user-persistence`、`bbs-user-facade`、`bbs-common` 打进 lib）。
3. 修改目标主机的 `bbs-user-service/application.yml`：ZooKeeper / MySQL / Redis 指向正确主机。
4. 原主机的 `bbs-rest`、`bbs-article-service` 的 `application.yml` 中 `dubbo.registry.address` 指向同一个 ZooKeeper，并更新 facade 依赖版本。
5. 依次启动 ZooKeeper → MySQL/Redis → auth → article-service / user-service → bbs-rest，验证接口可通。

## 四、一句话总结

- **实现方式**：Dubbo + ZooKeeper 做 RPC 与服务发现，Maven 多模块按 `facade（契约）/ persistence（数据）/ service（实现）` 三层拆分出 4 个可独立部署进程，`bbs-rest` 作为 REST 网关统一对外，`bbs-auth` 作为自托管鉴权服务。
- **拆分时**：**分离（带走）** 每个服务的 `*-service` + `*-persistence`；**保留（共享）** `bbs-common` 和所有 `*-facade`（契约必须发布到私服共享）；**重点改** 各服务 `application.yml` 中的 ZooKeeper/MySQL/Redis/MongoDB 地址，让它们跨主机通过同一个注册中心互相发现。
